## 1. 项目背景与目标

### 1.1 背景

原工作区有 11 个各自独立、技术栈不一的股票研究项目。它们各自解决了一个具体问题，
但也带来明显的重复与割裂：

* **数据层重复**：11 个项目里有 7 套自己实现的行情抓取代码，字段口径、单位（手/股、元/万元/亿元）、
  复权方式（前复权/不复权）互不一致，同一只股票在不同项目里可能得到不同的涨跌幅；
* **运维重复**：每个项目都要单独部署、单独配置、单独监控，本机端口从 5000 到 8899 各不相同；
* **能力无法复用**：A 项目的选股结果无法直接被 B 项目的回测验证，情绪周期结论无法驱动 C 项目的推送；
* **质量参差**：部分项目缺少测试，部分存在回测前视偏差与死参数，数据源单一、单点故障即整体不可用。

### 1.2 目标

把 11 个项目**归一化整合为一个可部署、可验证、可长期运行的单体平台**，实现：

| 编号 | 目标 | 达成标准 |
|---|---|---|
| G-1 | 统一数据底座 | 一套模型、一套单位口径、一套复权口径；所有策略共用同一条取数链路 |
| G-2 | 能力无遗漏 | 11 个项目的核心能力全部落地（见第 2 章能力矩阵），且可追溯到来源文件 |
| G-3 | 多源容灾 | 核心能力至少 2 个独立数据源；单源故障不影响整体可用；支持手动切换与手工录入地址 |
| G-4 | 进程可视 | 内存占用、缓存、定时任务、数据源健康度、慢请求全部可见 |
| G-5 | 一键部署 | 一条命令完成部署，且**直接部署与 Docker 部署两种方式都支持** |
| G-6 | 可验证 | 自动化测试覆盖核心算法与全部接口；提供部署后自检页面 |
| G-7 | 长期可跑 | 7×24 小时运行不内存膨胀、不因单点故障崩、不因上游限流整体失效 |

### 1.3 明确不做的事（避免预期错位）

| 不做 | 原因 |
|---|---|
| 自动交易 / 券商下单 | 本平台只做研究与辅助决策，不接交易通道 |
| 荐股与收益承诺 | 合规红线；复盘报告内置合规校验，出现荐股式表述即判定不通过 |
| 用户注册与权限体系 | 单机自用模型，默认免登录（可选开启管理口令） |
| 多租户 / 集群 | 单实例设计，行情轮询与定时任务假设只有一个写者 |
| 分钟级 / tick 级回测 | 回测基于日线；分钟数据仅用于展示 |
| 期货、期权、可转债 | 本期只覆盖沪深京 A 股与主要指数 |

### 2.2 能力归一化：五套策略 + 一个市场引擎

整合后的业务能力收敛为 **5 个选股策略 + 1 个市场级情绪引擎**：

| 策略 key | 名称 | 来源项目 | 类型 | 核心口径 |
|---|---|---|---|---|
| `trend` | 趋势狙击 | TrendSniper | 趋势跟随 | 十维加权：赛道/基本面/均线多头/阶段新高/月涨幅/换手/回调低点抬高/量能/相对强度/抗跌；止损三选一取最大 |
| `quiet_rise` | 潜涨雷达 | QuietRiseScanner | 低波动潜伏 | `0.30×Trend + 0.20×Volume + 0.20×LowVol + 0.15×RS + 0.15×Attention`，子分全部为连续函数；板块共振 +5~10 |
| `limit_up_pullback` | 涨停回调低吸 | Limit-Up-Pullback-Buy-Setup | 形态反转 | 优质首板八分类 + 五信号（缩量/支撑/企稳/筑底/板块）必须全部通过 |
| `n_pattern` | N 字战法 | NPatternStrategy | 形态突破 | 倍量点火 → 缩量回调 2~6 天不破点火低点 → B1 回踩 / B2 放量突破确认 |
| `pattern` | 形态扫描 | stock-pattern-discovery | 形态库 | 16 套经典入场形态 + 统一强度加成规则 + ATR 止损模板 |
| `emotion`（引擎） | 情绪周期 | 92KeBi + StockTradingReviewTool | 市场级 | 加权情绪分 0~100 + 五阶段周期（冰点/启动/发酵/高潮/退潮）+ 龙头四分层 |

| F-141 | **自选软删除与历史自选池** | 移出自选必须软删除并保留完整历史：`watchlist.removed_at` + `status`，另立 `watch_event` 事件流水（add/remove + 时间戳 + 交易日）。**踩过的坑：原先是硬删除，"何时进的、何时出的、期间涨跌多少"永久丢失**。重新加入时清掉历史行、`added_at` 记为本次时间，而事件流水保留全过程 |
| F-142 | **按日回顾（日历）** | 行情中枢、情绪周期、我的持仓三处均提供日历，可手动选择交易日回看当天数据。快照只覆盖确有留存的日期，因此日历下拉**只列有数据的交易日**并提供「最新」与「补写快照」。**情绪分未按日留存，页面须明确说明不提供历史情绪分，不得伪造** |
| F-143 | **静态资源版本号必须覆盖所有 HTML 页面** | 不能只有首页注入 `{{ASSET_VERSION}}`。**踩过的坑：`/selfcheck` 用 `FileResponse` 直出原始 HTML，绕过了 `_render_index()` 注入 —— 页面引用的是无版本号脚本，浏览器拿旧缓存配新后端，用户一点就报错且硬刷新未必修得好**。新增页面必须走同一渲染路径 |
| F-144 | **历史绩效回放** | 策略历史胜率/盈亏比必须按**该策略自己的风控模板**回放出场（复用回测引擎 `_check_exit`），不得用"持有 N 天"这类统一口径 —— 否则历史胜率与回测胜率口径不一致。入场价取扫描日**之后**第一个交易日开盘价（扫描在收盘后执行），成本按统一口径计入。**扫描历史是前向积累的（`build_market_context` 只认当日快照，无法回填）**，因此样本为空时必须说明真实原因，不得显示一堆 0 让人误判策略无效 |
| F-145 | **绩效归因** | 必须给出胜率差/盈亏比差的**原因**：按离场原因、持有天数、入选评分、板块、建仓月份分桶对比，并据数据生成可执行建议（如"止损占比过高且贡献多数亏损 → 放宽 ATR 倍数或改结构性止损"）。建议只说实话，不硬凑条数 |
| F-146 | **平仓即时结算** | 模拟持仓平仓后**立即**返回该笔结算（盈亏/持有天数/判定）与**同策略历史样本对照**及优化意见。单笔无法谈胜率，必须放进样本里看 |

## 4. 数据与单位口径（必须统一）

> 这是整合过程中**最容易出错**、也是原 11 个项目最不一致的地方。以下口径为强制约定。

| 项目 | 统一口径 | 各源差异与换算 |
|---|---|---|
| 成交量 | **股** | 东财/腾讯返回"手"→×100；新浪/同花顺/雅虎返回"股"→原值 |
| 成交额 | **元** | 东财=元；腾讯=元；新浪=元 |
| 市值 | **元** | 东财/新浪=元（新浪是万元→×10000）；腾讯=亿元→×1e8 |
| 涨跌幅 | **百分数**（`3.5` 表示 3.5%） | 多数源直接给；新浪实时行情需自行计算 |
| 换手率 | **百分数** | — |
| 复权 | **前复权（qfq）** | 东财 `fqt=1`、腾讯 `qfq`、新浪**不复权**（差异已记录，见 RISK-05） |
| 日期 | `YYYY-MM-DD` | 东财/腾讯 K 线为 `YYYY-MM-DD`；东财涨停池为 `YYYYMMDD`；同花顺为 `YYYYMMDD` |
| 时间 | 北京时间（UTC+8 固定） | 与服务器时区无关，显式换算 |
| 代码 | 6 位数字 | 支持 `600519` / `sh600519` / `600519.SH` 三种写法互转 |
| 北交所 | 代码段 `920xxx` / `83x` / `43x` / `87x` / `88x` | **必须识别为 `bj`**，否则涨跌停幅度会按 10% 算（实际 30%） |
| 涨跌停幅度 | ST 5% / 主板 10% / 创业板 20% / 科创板 20% / 北交所 30% | 集中实现于 `core/util.limit_pct` |

## 6. 技术架构

### 6.1 技术选型

| 层次 | 选型 | 理由 |
|---|---|---|
| 后端 | Python 3.12 + FastAPI + Uvicorn | 异步、自动 OpenAPI、Pydantic 校验；与原项目技术栈一致 |
| HTTP | httpx（异步） | 连接池复用 + 超时/重试可控；**不使用 HTTP/2**（实测部分行情网关对 h2 协商异常） |
| 计算 | NumPy | 指标与策略向量化；避免 pandas 在热路径上的开销 |
| 存储 | SQLite（WAL） | 单机零运维、单文件备份；写操作收敛到线程池 |
| 前端 | 原生 HTML + CSS + JavaScript | **零构建、零 CDN、零外部依赖**；图表自研 Canvas |
| 任务 | 自研 asyncio 调度器 | 交易时段/非交易时段双档节奏；不引入 APScheduler 等额外依赖 |
| 部署 | Docker（多阶段）+ systemd | 两种方式都提供，脚本自动选择 |

**设计原则：依赖越少越好。** 生产依赖只有 5 个（fastapi、uvicorn、httpx、numpy、psutil），
可选依赖 2 个（akshare、Ashare）。原 `stock-pattern-discovery` 的"零第三方依赖"经验被沿用到了前端。

### 6.2 分层与依赖方向

```
core  →  providers  →  engines  →  services  →  api
```

严格单向，不允许反向依赖：

| 层 | 职责 | 关键文件 |
|---|---|---|
| `core` | 路径、缓存、内存护栏、HTTP 客户端、代码/时段工具 | `paths.py` `cache.py` `memory.py` `http.py` `util.py` |
| `providers` | 16 项能力的多源实现与能力路由 | `base.py` `endpoints.py` `registry.py` + 各源模块 |
| `engines` | 指标、5 个策略、情绪引擎、复盘、回测、扫描编排 | `indicators.py` `base.py` `trend.py` … `scanner.py` |
| `services` | 面向用例的聚合：行情服务、用户数据、推送、调度 | `market_service.py` `user_service.py` `push_service.py` `scheduler_service.py` |
| `api` | HTTP 路由与统一响应信封 | `response.py` + `routes/*.py` |
| `store` | SQLite 持久化与用户设置 | `db.py` `kline_store.py` `settings_store.py` |
| `web` | 零构建前端 | `index.html` `assets/*` `selfcheck.html` |

### 6.3 数据流向

```
用户请求
   │
   ▼
api/routes/*  ──►  services/*（聚合 + 缓存）
                        │
                        ├─► engines/scanner（编排：上下文 → 并发评估 → 落库）
                        │        │
                        │        └─► engines/*（策略：纯函数，输入 Series 输出 Signal）
                        │
                        └─► providers/registry（能力路由）
                                 │
                                 ├─ 候选排序：配置顺序为主序 + 健康度微调
                                 ├─ 逐个尝试：首个通过 validator 的结果即返回
                                 ├─ 失败切换：记录 switch_event 供页面展示
                                 └─ 缓存：内存 → 磁盘 → 上游
```

### 6.4 关键设计决策（含取舍）

| 决策 | 取舍 |
|---|---|
| 日线只存日线，周/月线本地聚合 | 少一个口径要维护，避免"周线缓存与日线缓存不一致"；代价是聚合有极小的 CPU 开销 |
| 指数与个股分开取 | 避免"平安银行被当成上证指数"（实测 bug）；代价是多几次请求 |
| 合成数据必须显式开启 | 宁可在上游全挂时明确报错，也不把假数据当真实数据；代价是离线演示要手动切模式 |
| 候选顺序以配置为主、健康度为辅 | 避免"快但字段残缺的源"挤掉"稍慢但字段完整的源"（会让策略拿不到需要的字段） |
| 结果校验（validator） | 识别"不报错但数据不全"，这是免费行情源最常见的问题形态 |
| 前端零构建 | 部署极简（单进程单端口）；代价是页面用原生 JS 手写，没有组件生态 |
| 回测默认次日开盘 | 规避未来函数；与原项目大多"信号日收盘成交"不同，因此会**看到与原项目不同的回测数字** |

| 单源故障可恢复 | 临时改坏某源地址 | 自动切换到备源；页面显示切换历史；恢复后源重新参与 |

## 10. 风险与已知限制

> 本节如实列出**已知的不足**。这不是免责，而是让使用者知道边界在哪里。

| 编号 | 风险/限制 | 影响 | 应对 |
|---|---|---|---|
| RISK-01 | 免费行情源不稳定，且**不同网络环境下可达性不同**（本机实测：东财主域名被 TLS 阻断但 delay 镜像可达；腾讯部分 K 线入口返回 501） | 某些源在特定服务器上不可用 | 多源容灾 + 每源多入口 + 健康度排序 + 数据源诊断工具（`tools/probe_sources.py`）；换环境后先跑一次探测 |
| RISK-02 | 新浪全市场列表接口高频访问会返回 HTTP 456（封禁约 10 分钟） | 该源暂时不可用 | 收到 456 时自动把 host 标记冷却；列表一天只需抓一次并落盘；东财为列表主源 |
| RISK-03 | 指数与个股代码段重叠（`000001` 既是上证指数也是平安银行） | 用股票快照匹配会显示错误标的 | 指数走独立接口 + 显式 secid 映射表；已有回归测试断言指数名称与点位量级 |
| RISK-04 | 不同源的成交量/成交额/市值单位不同（手/股、元/万元/亿元） | 单位不统一会让策略阈值失效 | 全部在 provider 解析层归一化为"股/元/元"，并有测试覆盖 |
| RISK-05 | **复权口径不完全一致**：腾讯/东财/同花顺为前复权，新浪日 K 实测为不复权 | 除权日附近新浪 K 线会出现跳空，影响均线与形态判定 | K 线主源用腾讯（前复权）；同一轮扫描建议不要混用不同源；页面显示实际生效源 |
| RISK-06 | "情绪温度计"在原始项目里有**三种不同语义**（阶段置信度×100 / 加权情绪分 / LLM 主观评级） | 直接混用会得出矛盾结论 | 本平台只采用"加权情绪分 0~100"口径，并同时给出周期阶段，二者语义在页面明确区分 |
| RISK-07 | 情绪周期阈值依赖**样本口径**（原 92KeBi 用"成交额前 500 只"折算全市场） | 小额成交标的的情绪贡献被淡化 | 默认全市场覆盖（`universe_size=0`）；受限采样时响应带 `sample_limited=true` 并在页面标注 |
| RISK-08 | 回测**默认次日开盘成交**，与多数原项目"信号日收盘成交"不同 | 与原项目的回测数字不可直接对比 | 页面提供口径切换；两种口径都明确标注；默认口径无未来函数 |
| RISK-09 | 回测存在**幸存者偏差**（股票池取自当前快照，已退市/长期停牌标的不在样本内） | 历史收益可能被高估 | 页面明示；不用于收益承诺 |
| RISK-10 | 部分财务与关注度数据为可选能力，未接入时策略按中性处理 | 相关维度不参与打分而非被错误扣分 | 条件明细中明确标注"不可得(中性处理)"；数据源页显示该能力无可用源 |
| RISK-11 | 全市场首次建立日线缓存需要数分钟 | 部署后首次选股较慢 | 启动后台预热；磁盘缓存只补增量；`TimeoutStartSec=900` 避免被 systemd 误杀 |
| RISK-12 | SQLite 为单写者模型 | 不支持多实例并发写 | 明确单实例部署；容器复制的场景需各自独立数据卷 |
| RISK-13 | 上游接口随时可能变更（字段、路径、反爬策略） | 某源突然不可用 | 地址集中在唯一文件、可页面覆盖；字段解析失败会明确报错而不是产出错数据；提供响应结构核对工具 |
| RISK-14 | 行情存在延迟（东财 delay 镜像为延时行情） | 不适合超短线实时决策 | 页面显示实际生效源与数据时间；定位是研究工具 |
